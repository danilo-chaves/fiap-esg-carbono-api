2. Descrição do Pipeline CI/CD

O fluxo de automação foi projetado com GitHub Actions, dividindo as responsabilidades de forma clara entre Integração Contínua (CI) e Entrega Contínua (CD), com suporte nativo a dois ambientes distintos: Staging e Produção.

Fluxo Automatizado de Entregas:

1. Git Push / PR ➔ 2. CI: Build (Maven) ➔ 3. CI: Testes (JUnit/H2) ➔ 4. CD: Docker Multi-Stage ➔ 5. Registry Push ➔ 6. Deploy Staging (develop) / 7. Deploy Produção (main)

2.1 Etapas do Pipeline de CI (continuous-integration.yaml)

  • Build Automático: O workflow realiza o checkout do código, instala o JDK 21 (Temurin) e executa mvn clean compile, validando sintaxe e dependências.
  • Testes Automatizados: Executa mvn test com 9 testes automatizados (testes unitários com Mockito para as regras de negócio e teste de contexto com banco em memória H2). Isso assegura execução veloz (< 30s) sem dependência externa.
  • Publicação de Relatórios: Upload automatizado dos relatórios Surefire para rastreabilidade de qualidade.

2.2 Etapas do Pipeline de CD (continuous-delivery.yaml)

  • Build de Imagem Docker: Acionado a cada push em develop ou main, gerando a imagem otimizada via Dockerfile multi-stage.
  • Deploy Automatizado em Staging: Quando a branch de origem for develop, o artefato é publicado no ambiente de Staging (com tag :staging e :staging-<sha>) para homologação prévia.
  • Deploy Automatizado em Produção: Ao realizar o merge na branch main, o pipeline aciona o ambiente de Produção (com tag :production e :latest), validando a publicação final.

3. Containerização e Orquestração (Docker)

A aplicação foi empacotada utilizando Multi-Stage Build para otimização de imagem e governança de segurança:

# Estágio 1: Build (Maven + JDK 21)
FROM maven:3.9.6-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src
RUN mvn clean package -DskipTests

# Estágio 2: Runtime Minimalista (JRE 21 Jammy)
FROM eclipse-temurin:21-jre-jammy
WORKDIR /app
COPY --from=build /app/target/carbono-api-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

A orquestração local é feita através de docker-compose.yml contemplando:

  • Serviços: oracle-db (Oracle Free 23ai) e carbono-api (Aplicação Spring Boot).
  • Healthcheck: O contêiner da aplicação aguarda a inicialização completa do banco através de depends_on.condition: service_healthy.
  • Volumes & Redes: Volume persistente oracle_data para garantir retenção de dados e rede bridge esg_network para isolamento de tráfego.
  • Configurações: Variáveis de ambiente configuráveis através de .env e documentadas em .env.example.

4. Desafios Encontrados e Resoluções Técnicas

Desafio Enfrentado Causa Raiz Solução Implementada
Falha no teste automatizado durante CI O contexto do Spring tentava conectar no listener do Oracle local (porta 1521), inexistente no runner do GitHub. Configuração do perfil test com banco in-memory H2 e criação de testes unitários isolados com Mockito para os serviços de Domínio.
Imagem Docker com tamanho elevado Inclusão de compilador JDK e ferramentas de build no contêiner produtivo. Estratégia de Multi-Stage Build, reduzindo a imagem final para apenas o JRE 21 leve (Ubuntu Jammy).
Dependência de inicialização do banco A aplicação subia antes do listener do Oracle estar pronto para receber conexões. Configuração de healthcheck oficial com retries no banco e bloqueio de subida na API via Docker Compose.
